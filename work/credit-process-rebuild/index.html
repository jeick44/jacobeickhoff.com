Credit Process Rebuild

Loan origination — intake, tax-document extraction, spreads and the approval presentation — is being rebuilt as browser tools that run entirely on the analyst’s own machine, under a governing condition that no customer data reaches a cloud service and no tool requires a server.

The Situation

A lender submits a request for a new loan, a renewal or a modification. An analyst turns it into the presentation a credit committee decides from. Everything in between moves through a chain of spreadsheets and a shared drive, and none of it is written down — so one concept can carry two definitions in one workbook and nothing notices.

The constraint arrives before any design does: no customer data reaches a cloud service, and no tool requires a server. I treat that as the starting point rather than an obstacle to route around, because the reasoning behind it is a threat model and not an IT preference.

Why the constraint is about concentration, not connectivity

The case for a server is convenience; the case against it is concentration. A compromised workstation yields only what that analyst could already open from the share. A compromised server yields every customer, because its service account has to read all of them and bypasses the share’s permissions by design.

It also turns a document on a share into a formal internal service, which at a regulated institution means risk assessment, sign-off and examiner scrutiny. The decision is recorded with the conditions that reverse it: someone outside the network needs access, concurrent editing becomes routine, or access control is needed finer than the share can express. None is true today.

What I Did

Origination is being rebuilt as nine browser tools. Each is a single HTML file opened from the shared drive, reading and writing customer files through the browser’s file access API — no server, no database, no network call. That is the primary security control, so it is not left to discipline: a check fails the build if a network call or an external resource ever reaches a shipped file.

Two pieces of the rebuild are process design rather than software. The first is the Three-Stage Review. The approval presentation used to be produced by doing three things at once: filling in the figures, working out why they look the way they do, and checking the result. Interleaved, every question the analyst cannot answer becomes an interruption — a call to the lender who wrote the deal, mid-analysis.

The Three-Stage Review, and the cost it is optimising

The rebuild separates them: fill the figures, analyse the why, then review. A question only the originating lender can answer is marked where it arises and re-listed in one place at the end, so a phone call is one phone call rather than a running string of interruptions.

The rationale is stakeholder cost: the scarce resource is somebody else’s attention, and a redesign that saves the analyst an hour by spending two of the lender’s has made things worse while looking better.

Extraction that refuses rather than guesses

The tax-document tool reads a return and produces a per-customer income statement with debt-service coverage. A scanned, image-only return is refused by name and pointed at the route that works, rather than run through character recognition and emitted as numbers that look like figures. Where an export has scrambled a line’s description, the amount is flagged for review instead of attached to the nearest plausible label.

The rule underneath both: in a credit file a wrong number costs more than a missing one, because a missing number is visibly missing and a wrong one is what everybody works from.

What Changed

Measured, and mine to state: nine tools shipped; 3,923 automated assertions over the approval-presentation tool alone, none failing, with a second harness that proves them capable of failing by injecting the faults they exist to catch; nine architecture decisions written down, each with the alternative it was chosen over.

Pending Results Time from request to committee, lender callbacks per file, and the rate of corrected figures in a finished presentation are real effects of this work, and none of them has a before-and-after measurement I would stand behind. They are labelled rather than estimated, and this paragraph gets replaced when there are numbers.

What I Learned

That a green test suite tells you the tests passed, and nothing else.

One change generalised part of the spreads import so a new kind of financial tab could share machinery the existing ones used. It worked, and the suite was green. A code review of that same change found six defects, two of which would have corrupted figures on their way into a credit decision.

The six, and the pattern underneath them

The two that would have reached real figures. The test deciding what kind of sheet the tool is looking at asked its question of the whole sheet rather than the header band, and a block of round four-figure expense amounts reads to it as a row of years. A real sheet would have been typed wrongly and handed to a parser that keys columns by year, so two properties would land on one key, one silently overwriting the other, and the survivor would merge into that company’s genuine multi-year trend. And the migration that carries old data into the new shape verified the carry before deleting the original by comparing an object with itself — a comparison that could not fail, and the only gate on deleting the analyst’s hand-entered grid.

The other four: a refusal with nowhere on screen to be said; a rule that had quietly stopped being true for one sheet type; a predicate rewritten into a form that read the same and changed behaviour under cover of fixing a fifth case; and three analyst-facing messages printing an internal key instead of a name.

All six sit in code that generalised an existing rule, which is the pattern worth naming: the rule goes on reading correctly while the predicate underneath it has changed meaning.

The useful part is not the six. It is that the suite, the mutation harness and I were all satisfied, and reading the change as prose was what was left. I write the tests and I still need the review.

Where Else This Applies

Arguing a constraint’s threat model rather than accepting its conclusion. Healthcare, legal and defence work runs under conditions that look like obstruction from outside and are load-bearing from inside, and knowing which is the difference between negotiating a constraint and building within it.

Separating a process by whose attention it spends. Any workflow where one role waits on another’s answers has the interleaving problem, and the measure of a redesign is total interruption, not hours saved by whoever redesigned it.

The refusal rule. Any pipeline turning documents into figures somebody decides from — claims, invoices, applications, filings — chooses between producing a number and admitting it cannot. A system that guesses reads exactly like one that knows, until someone checks an output it has already been acted on.
